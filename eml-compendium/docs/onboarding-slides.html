The Pragmatic Programmer

Pragmatic Attitude

Take Responsibility

  • Your career: Own your learning and growth
  • Your code: You're accountable for what ships
  • Your decisions: Provide options, don't make excuses
  • Your mistakes: Admit honestly, offer solutions

Software Entropy

  • Broken windows: One bad design decision invites more
  • Don't live with it: Fix bad code when you see it
  • Keep it clean: Pristine code encourages careful work
  • Fight decay: Small fixes prevent large rot

The Pragmatic Programmer

DRY — Don't Repeat Yourself

  • Every piece of knowledge must have a single, unambiguous, authoritative representation
  • Not just code — applies to documentation, data schemas, API specs, configuration
  • Test: When one thing changes, do you have to update multiple places?
  • Duplication is the enemy — creates maintenance burden and contradictions
  • Abstract wisely — but don't force premature abstractions

Example: Constants in one file, utility functions in shared modules, API types generated from schemas

The Pragmatic Programmer

Orthogonality & Decoupling

What is Orthogonality?

  • Components are independent — changes in A don't affect B
  • Write "shy" code — modules don't reveal unnecessary details
  • Reduce interdependency between system parts

Benefits

  • Productivity: Changes are localized, components reusable
  • Risk reduction: Diseased code isolated, system less fragile
  • Testing: Test modules independently
  • Flexibility: Not tied to specific vendors or platforms

The Pragmatic Programmer

Tracer Bullets & Structured Discovery

  • Tracer bullets: Thin, end-to-end implementation through all layers
  • Use when you're not 100% sure where you're going
  • Small body of code has less inertia — easier to adjust aim
  • Get immediate feedback from users and stakeholders
  • Different from prototypes — tracer code is production-ready, kept and refined

EML Application

Build one complete user flow first (e.g., one EPISODE scenario end-to-end)

Then replicate the pattern for additional features

Validates architecture early, reduces risk

The Pragmatic Programmer

Design by Contract

Contracts Define Expectations

  • Preconditions: What must be true before function runs
  • Postconditions: What function guarantees when done
  • Invariants: What remains true throughout

Use Assertions

  • Validate inputs at function boundaries
  • Check assumptions explicitly in code
  • Fail fast when contracts violated
  • Document expectations through code

Example: TypeScript types are contracts, assert statements check runtime conditions

The Pragmatic Programmer

Basic Tools: Your Toolkit

Text Manipulation

  • Master one editor: Notepad, VS Code, Vim — the tool matters less than your proficiency
  • Learn it deeply: Keyboard shortcuts, search/replace, multi-cursor, refactoring
  • Text is universal: Configuration, code, documentation, logs — all text
  • Invest the time: Efficiency compounds over your career

Source Code Control

  • Always use version control: Even for solo projects, even for "just trying something"
  • It's your safety net: Undo anything, see what changed, experiment fearlessly
  • Collaboration foundation: Multiple people, one codebase, no conflicts
  • Time machine: Go back to any point in history, understand why changes were made

EML standard: Git + GitHub. The principles apply to any version control system.

Technical Foundations

HTTP & REST APIs

HTTP Basics

  • Request/Response: Client asks, server answers
  • Methods: GET (read), POST (create), PUT/PATCH (update), DELETE
  • Status codes: 2xx success, 4xx client error, 5xx server error
  • Headers: Metadata like authentication, content type

REST Principles

  • Resources: Everything is a resource with a URL
  • Stateless: Each request is independent
  • JSON: Common data format for APIs
  • EML example: EPISODE uses AWS Bedrock API for LLM, Polly for speech

Resources: MDN Web Docs (HTTP), REST API Tutorial

Technical Foundations

Computer Graphics Rendering Pipeline

  • 1. Vertices: 3D points define object geometry
  • 2. Vertex Processing: Transform to screen space (world → view → projection)
  • 3. Rasterization: Convert triangles to pixels (fragments)
  • 4. Fragment Processing: Calculate color, lighting, textures per pixel
  • 5. Output: Final pixels written to screen

EML Applications

VestibuLearn: Unity handles pipeline for VR rendering (2 views per frame for each eye)

IMLE: Three.js/React Three Fiber uses WebGL pipeline for 3D molecules

Both use same fundamental pipeline, different APIs

Resources: learnopengl.com, WebGL Fundamentals, Three.js docs, React Three Fiber docs, Unity Graphics Documentation

Technical Foundations

State Management Patterns

What is State?

  • State: Data that changes over time (user input, API responses, UI state)
  • Local state: Owned by one component
  • Shared state: Multiple components need access
  • Immutability: Don't modify state directly, create new copies

Patterns

  • Unidirectional data flow: State flows down, events flow up
  • State machines: Explicit states and transitions (Planetary Health uses this)
  • Context/Providers: Share state without prop drilling
  • Reducers: Predictable state updates

Resources: React docs (useState, useContext, useReducer)

Technical Foundations

Asynchronous Programming

Why Async?

  • Don't block while waiting for slow operations (network, file I/O)
  • Keep UI responsive during long tasks
  • Handle multiple operations concurrently

JavaScript Patterns

  • Callbacks: Pass function to call when done (oldest pattern)
  • Promises: Object representing future value (.then(), .catch())
  • Async/Await: Write async code that looks synchronous (modern, preferred)
  • Event loop: How JS handles async without threads

EML example: EPISODE uses async/await for AWS API calls (Bedrock, Transcribe, Polly)

Technical Foundations

Component-Based Architecture

Core Concepts

  • Composition over inheritance: Build complex UIs from simple pieces
  • Encapsulation: Component owns its logic and state
  • Reusability: Write once, use many times
  • Single responsibility: Each component does one thing well

Data Flow

  • Props: Data passed from parent to child (read-only)
  • Events: Child notifies parent of changes
  • Lifecycle: Mount → Update → Unmount
  • Both Unity and React: Use component model with different syntax

EML projects: React components in web projects, MonoBehaviours in Unity (VestibuLearn)

Technical Foundations

TypeScript Type Systems

Why TypeScript?

  • Catch errors early: Type errors at compile time, not runtime
  • Self-documenting: Types explain what code expects
  • Better tooling: Autocomplete, refactoring, go-to-definition
  • Scales well: Large codebases stay maintainable

Key Concepts

  • Primitives: string, number, boolean
  • Interfaces: Define object shapes (contracts)
  • Generics: Reusable types (Array<T>)
  • Union types: Value can be one of several types
  • Type inference: TS often figures out types automatically

All EML web projects use TypeScript. Resources: TypeScript Handbook, Total TypeScript
